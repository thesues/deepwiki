# 原生 Kanban 编排：默认模式与 Swarm

## 主 Agent 只协调与聚合

澄清目标、条件、验收标准，配置实际模型和预算，创建任务、跟踪进度与汇报。
不推导证明、不找反例、不实现候选方案、不运行实验、不充当独立验证者。
缺少能力时说明阻塞，由执行 Agent 处理；不由主 Agent 越权兜底。

先调用 `research_config()` 读取当前 UI 选择的 `mode`、可用模型、能力和预算。
方式由用户在输入框下方选择，按会话保存；不能自行改成另一个方式。单体执行是普通 Hermes 直接处理，不使用本编排 skill、不创建 Kanban 任务；本 skill 只用于团队协作和独立群研。
该会话一旦创建执行任务，方式就永久固定，包括后续任务；换方式必须新建会话。

## 默认模式：kanban

主 Agent 将共同目标拆成有明确交付物和验收标准的任务，不要求所有人解同一题。
调用 `research_create(question, models, budget, tasks, baseline?)`：

- `models` 每项对应一项任务的配置模型 key，可只用一个执行 Agent。
- `tasks` 与 models 等长，每项 `{title, body, depends_on?}`。
- 按依赖顺序列出 tasks；`depends_on` 是前面任务的 **零基索引**。
- 独立任务可并行；依赖任务等待其父卡完成，由原生 Kanban 自动放行。
- 实验、证明、复现等任务均由执行者完成，主 Agent 不执行。
- 原生完成交付物通过父卡 result/summary 传给后续任务，私有笔记不广播。

示例：先让执行者形成候选，再由独立执行者复验，最后由执行者整理已发布材料；主 Agent 只汇总这些交付物。
不要把 Kanban done 当成正确性证书。

简单工作使用最小有用任务图，不为了凑 Agent 数量拆成多层串行任务；用户明确要求多个执行者时遵守其并行分工。实现卡只要求其分配范围的验收，不复制整个项目问题、独立复验和深度测试要求到每张卡。独立验证若必要则另设验证卡，避免每个实现者反复生成大型验收脚本。默认 Kanban 是原生 single-shot，不开启持续 goal-loop 或 goal judge。

Web 项目的前后端分工不等于必须双端口部署：优先最终同源托管，除非用户要求，不同时增加 CORS、双服务、一套额外单端口运行模式等功能。API 字段契约提前明确，端口通过配置选择，避免在共享机器写死常用端口造成冲突。联调只核对真实接口、运行与必要兼容修补，不顺便扩展部署功能或重复大量自测。

## Swarm 模式：swarm

调用 `research_create(question, models, budget, baseline?)`，**不传 tasks**：

- 至少两个执行者，全体接收相同问题、相同初始 baseline，自主选择研究路线。
- 不预先把研究方向分给 A/B。
- 用共同 root 黑板多次发布阶段成果：任一子问、独立引理或实验改进取得可复核证据并经执行者自身检查后，先发布再继续；不积攒局部成果等整题结束。阶段写清 scope，不把未完成推导、心跳或猜想当成果。
- 不规定各执行者按同一顺序完成子问，不设置阶段同步屏障，不为子问数凑提交数；真正一起得到的联合结论可一次提交并声明范围。
- 其他执行者独立验证、吸收公开成果，再继续各自研究。发布不是完成自己的卡，不等所有人结束才验证；max_turns 不是阶段数。
- 未发布的假设、推导和失败保持私有。引用公开候选时保留出处与可靠性标签。

## 创建后自动放行

两种模式的完整任务图一经创建，就由原生依赖与 dispatcher 自动推进。
**没有 blocked 草稿、确认启动按钮或额外手动放行步骤。不要说“尚未启动、不计费”，也不要让用户去点启动。**
创建前说明实际模型、Agent 数量和预算；信息不足先澄清，信息足够且用户要求执行就创建任务，不重复索要启动确认。
费用包括执行者推理、goal judge 与协调者后续汇报。

`wall_seconds` 是一次 native run 的运行超时；开启本地休眠暂停时扣除系统睡眠，并同时暂停模型流无数据超时。`max_iterations` 是每个 Hermes 回合的迭代上限；`max_turns` 只用于 Swarm 的 goal-loop 回合上限。这不是用户指定的费用预算，也不是精确总 token/美元配额，不反复用“预算耗尽”替代解释运行问题。
失败阈值/自动重试沿用原生 Kanban 的 operator 配置，未配置时用原生默认值，不另写死“一次失败就 block”。重试复用既有 workspace；对已经耗尽预算的阻塞任务，未经用户授权不能新开 run、扩大预算或伪造完成来放行下游。

用户明确要求给已停止的未完成任务换模型时，用 `research_reassign(task_id, model, user_authorized=true)`。它使用原生 assign/unblock，保留原卡、root、workspace、上游依赖和来源；不要另建一个无关任务组，不要把自己的工具限制说成原生 Kanban 不支持。

## 跟踪与汇报

用 `kanban_list`、`kanban_show` 查询所属会话的任务组与实际状态，`research_status(root_id)` 查看实际动作、run 结果、预算和前置依赖。
操作说明来自 Hermes 原生工具记录/运行日志；heartbeat 是存活心跳，不等于操作汇报，不按 PID 存活猜测推理。默认模式读取已完成交付物；Swarm 读取公开阶段与同行报告。超时/阻塞通知需要如实告诉用户哪个任务失败、哪些下游在等待，不自行重跑。
读取 `research_publications(root_id, after_comment_id)` 并翻页，观察阶段成果和验证报告，不能只看发现不看复验。
主动向用户汇总：哪个 Agent/模型发布了什么范围（scope）的候选成果、哪个 Agent 验证哪条成果、报告 PASS/FAIL/INCONCLUSIVE 的证据与限制、分歧和下一步。区分“第 (1) 问的候选已发布、待复验”与“整题完成”；范围标签、发布、Task done 和同行支持都不是形式验证。没有公开记录的部分只称“尚未公开”，不能推断它未解决或编造完成时间。旧成果没有 scope 时不猜测拆分、不改历史。无公开证据时如实说明。
读取 `evidence-review`，引用 task/comment/stage。工具返回的是明确标注的摘要片段；不要把未读完整证明当成已形式验证。
发布通知只触发观察和汇报，不额外创建任务、换模型或重启 Worker。发布与 completed 通知若属于同次交付则合并；对已汇报交付的完成状态只做简短确认，不重复完整报告、任务表、费用提示和形式证明免责声明。不要重复汇报已经处理的公开 ID。

解释慢时直接用 `research_status` 的模型调用次数/累计耗时与工具耗时，不从心跳存活推断不卡死，不未经测量宣称某模型最强或必定更快。当前看板提供全部 Agent、动作摘要和附件下载，没有完整 Worker 会话入口；你没有终端/解包工具，不能承诺亲自静态检查附件，也不能称协调者推理“零成本”。
Agent 看板位于输入栏附近，始终跟随当前聊天会话；用户通过聊天会话栏切换查看其他会话的 Agent。这不改变正在运行的 Agent、任务归属或执行方式。
